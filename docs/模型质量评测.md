# 模型质量评测基线

此基线用于比较同一组输入在不同模型、提示词版本下的表现。所有输入均为虚构场景，不写入个人记忆。协议校验、语义评分和真实设备测试分别记录；自动化测试通过不能证明模型语义准确。

## 收集与评分

1. `npm start`，在应用设置页配置并启用模型。不要把密钥写入测试文件。
2. 执行 `npm run eval:model -- collect`。这会使用已配置的服务发起 **9 次真实工作流请求**，按服务商规则计费；只有手动执行 collect 才调用。可通过 `BANTING_URL` 指定其他本机端口。
3. 脚本逐例保存到独立的 `.local/qa/semantic-日期-ID/assessment.json`。请求失败也记录并继续；每次运行创建新目录，不覆盖上一轮。输出包含输入、评分标准、实际输出、模型、提示词版本和耗时，不包含密钥。
4. 人工逐例对照原始记录、补充和上下文，填写 `assessment.reviewer`、`reviewedAt`（ISO 日期）、`scores` 与 `notes`。默认所有评分为 `null`，表示待评；不可用脚本执行成功或引用存在替代判断。
5. `npm run eval:model -- report <assessment.json路径>` 汇总维度分数及状态。退出码：0=该基线通过；1=失败/格式错误；2=尚未评完。相同数据集版本、相同评分标准下再比较两个运行结果。

## 固定案例与标准

源文件：`tests/fixtures/semantic-cases.json`，版本 `semantic-baseline-v1`。

| 案例 | 工作流 | 人工重点检查 |
|---|---|---|
| speaker-boundary | 记录理解 | 嘉宾职业经历不归给用户；未决定不升级成已决定 |
| conditional-action | 记录理解 | 时间条件、可能性和否定必须保留 |
| correction-priority | 记录理解 | 使用补充限定含义，不把补充伪造为原话 |
| keyword-distractor | 历史关联 | 同有“练习”不能让网球与面试强行关联 |
| conditional-change | 历史关联 | 岗位条件变化不等于人格或价值观突变 |
| no-evidence | 问题回忆 | 无留学记录时承认无法确认，不断言从未考虑 |
| suggestion-not-history | 问题回忆 | 分开历史事实与可选建议 |
| no-forced-growth | 阶段回顾 | 两天情绪不能推出能力或长期成长趋势 |
| supported-tentative-change | 阶段回顾 | 有双时点证据时识别可能变化，仍保留不确定性 |

每项按0/1/2分：0=违背标准或造成误导；1=部分满足、仍需修正；2=完整满足。所有关键项须为2分，任何0分均不通过；全部完成、署名、填写日期后，平均分须至少1.5。当前基线全部为关键项，因此要求全部为2分。报告有缺失案例、缺失评分或未署名时不能通过。请在 notes 具体说明错误，不以措辞是否漂亮代替准确性。

## 证据边界

- 引用真伪仍由生产服务校验，评分工具不新增一个“AI裁判”。
- 案例中的音频上下文是明确标记的虚构材料，用于隔离语义判断，不验证 Whisper。
- `tests/semantic-evaluation.test.mjs` 只验证收集、待评、失败及评分汇总的行为，不产生真实模型质量结论。
- 一次9例通过仅代表该轮基线表现；扩大到真实用户场景前，还应增加经过授权、去标识化的失败案例，重复运行并人工检查稳定性。更改案例或标准时更新数据集版本。
